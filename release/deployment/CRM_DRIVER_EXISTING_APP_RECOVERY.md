## Pure plan and snapshot checks

`target_update_plan` returns a PRIVATE spec copy, not a printable report.
It permits exactly four value changes: the service image digest, GENERAL
`CRM_CANARY_DRIVER_VERSION_SHA256`, and two login SECRET values reconstructed
from the authenticated original fixture with exactly integer `schema_version: 1`
added. Original emails and passwords are identical; no credential or HMAC is
generated or rotated. The fixture descriptor, HMAC and Meta SECRET ciphertexts
remain byte-for-byte unchanged. Fixed ledger binding, resources, health,
ingress, features and all remaining fields remain unchanged. The planner
independently reverts all four deltas and compares canonical bytes with the
original provider representation.

The plan contains two new private plaintext login JSON values and three old
opaque ciphertexts, solely in memory. Exact reconstructed login bytes are
checked separately; a structural-validation copy uses the original two login
ciphertexts because shared readback projection accepts only provider ciphertext.
This substitution is a validation technique, not decryption or proof of future
ciphertext identity. Never print, persist or hash the private update body.

Two genuine snapshots must be spaced 3–120 seconds, with the latter no more than
120 seconds old and both inside fresh authority. They must agree on owner,
inventory, both old deployment specs, opaque ciphertext, routing/feature
representation, admitted firewall, fixture/canary metadata and production state.
The resulting target plans must also agree in memory. Matching ciphertext does
not prove decryption or a runtime HMAC round trip.

Inspection reports only fixed codes and public authority/image identities.
The fixed `SCHEMA_VERSION_MISSING` finding is explicitly labelled
`source-construction-only`, not decrypted live provider configuration.
It always reports `ready_for_operation: false`, `ready_for_finalize: false`
and `mutation_performed: false`. Remaining observed blockers are deployment
